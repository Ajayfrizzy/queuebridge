## Service worker lifecycle

In a sixth, empty context with workers enabled, navigated directly to the valid join URL. BrowserContext request events with a serviceWorker owner identified requests for LandingPage-B45ie02v.js and LandingPage-CfAgQNc7.css. After navigator.serviceWorker.ready and controller acquisition, Cache Storage contained both URLs. The landing pair represents 27,769 gzip comparison bytes. The Workbox build listed 24 entries (1041.85 KiB uncompressed). Manifest size is distinct from network transfer; worker-request wire totals were not captured.

A controlled warm join reload rendered the ticket button. Entry JS and registerSW.js both had workerStart above zero and transferSize zero. After setting the context offline and navigating directly to join again, the seeded clinic heading rendered. This establishes cached shell and public facility access after the warm visit. New offline staff commands, an unseen facility and offline first-ever installation were outside this measurement. The blocked-worker join trace contains neither landing asset. Thus the eager background download comes from precache installation. Source: apps/web/vite.config.ts and apps/web/src/pwa/swRules.ts.

**Proposed implementation order, subject to review**

1. Put staff console, connectivity, audit, facility configuration and admin screens behind route imports in apps/web/src/App.tsx. Keep the signed-in gate and tenant checks ahead of protected rendering. Staff-specific fairness and recovery controls should follow their importing screens. Verify signed-out redirects, authorized console entry, stable layout/focus, offline staff reopening and old-shell/new-chunk update handling. Expected benefit is removal of staff/admin source from anonymous startup. Shared dependencies may remain.
2. Give signup, login, invitation, board, join, recovery and ticket independent route entries. Keep HTML preferences, route announcements, safe loading states and minimal session resolution eager. Preserve fragment capture/scrubbing before asynchronous work on recovery entry. Load QR generation with the first screen or action that needs it, including visitor recovery and staff walk-in. Test rapid navigation, refresh, printed/scanned recovery keys, offline reopening and dialog focus. Ticket-specific work still counts on ticket entry.
3. Inspect runtime contract imports down to individual schemas. The graph includes Zod 4.6.7 and cross-feature contracts. Preserve strict validation and the jitless initialization in src/zodConfig.ts before any parse under CSP. Verify malformed input, strict CSP and the existing contract tests. React DOM and routing remain startup dependencies under the approved architecture. Measured framework and validation costs make achievement by route splitting alone uncertain.
4. Keep Ask Que's launcher available and its existing QuePanel/publicKb boundaries. Verify keyboard and offline opening, anonymous article access and user-specific restricted content on sign-out. Narrow remaining eager registry imports only after checking callers. Preserve the shared reachability observer, session-change behavior, IndexedDB isolation and coordinator fencing. Consider deferring staff-only coordinator machinery behind authenticated use only after proving cold offline reload, retry and reconciliation across a version upgrade. Moving the entire offline provider would risk startup correctness.
5. Review precache policy independently. A candidate is to exclude only landing-specific assets from eager install and cache them on first landing use. Decide whether first-ever offline landing on a device installed from join is required. Keep critical staff/visitor/offline chunks available before advertising offline readiness. Validate worker install/update, stale HTML, multiple tabs, offline navigation and absence of protected API data in Cache Storage.

Each proposed boundary requires explicit implementation approval. Measure the actual cold route sums after each accepted change. A renamed or extracted shared chunk still counts. Savings have no measured value until a candidate exists. Acceptance requires both join and ticket under 100,000 gzip bytes, correct startup content, no unexpected landing fetches and passing security, accessibility and offline regressions.

## Health and readiness dependency

apps/api/src/app.ts registers anonymous /health and /health/ready without explicit route limits. Readiness queries PostgreSQL. The visitor reachability logic in apps/web/src/lib/api.ts relies on an answered /health probe after outage. Before selecting protection, obtain RumptyCloud ingress reachability for both paths, monitor source identity, interval, burst and timeout, proxy trust and replica behavior. Verify that browser recovery probes work behind shared NAT and that internal readiness checks continue during rollout. Decide with the owner whether readiness can be private and whether public liveness needs a monitor-aware edge limit.

## Lighthouse CLI protocol and observations

Pinned Lighthouse 12.8.2 in an isolated temporary npm installation. Used Playwright's full Chromium executable, the same preview, a fresh CLI browser for each sample and alternating landing/join order. Default mobile emulation was 412 × 823, DPR 1.75. Simulated throttling used RTT 150 ms, throughput 1638.4 Kbps and CPU multiplier 4. Local emulation provides a repeatable lab baseline. Hosted and physical-device timings require separate evidence.

```sh
npm install --prefix /tmp/qb-b1 --ignore-scripts --no-audit --no-fund lighthouse@12.8.2
export CHROME_PATH="$(node -p "require('./apps/web/node_modules/@playwright/test').chromium.executablePath()")"
# Set JOIN_PATH to the seeded clinic join path; run from the repository root.
for i in 1 2 3; do
  for route in landing join; do
    pathpart=/
    if [ "$route" = join ]; then pathpart="$JOIN_PATH"; fi
    /tmp/qb-b1/node_modules/.bin/lighthouse "http://localhost:4192$pathpart" \
      --only-categories=performance --throttling-method=simulate \
      --chrome-flags="--headless --disable-extensions" --quiet \
      --output=json --output-path="/tmp/qb-b1/$route-$i.json"
  done
done
```
