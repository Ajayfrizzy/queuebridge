# M7.3-B4 staff schema isolation

Local uncommitted candidate on feature/m7-3-hardening, base 5d2e5ea plus accepted B2/B3 work. **Isolating facility-readiness response schema construction saved only 102 gzip bytes in the shared entry.** The experiment stopped at this family.

## Dependency and scope

One concrete runtime path is apps/web/src/App.tsx → offline/OfflineProvider.tsx → @queuebridge/continuity → packages/continuity/src/authority.ts → CoordinatorAuthSchema from @queuebridge/contracts → packages/contracts/src/index.ts → its admin.js re-export → FacilityReadinessSchema. Rollup retained the nested Zod constructor calls when evaluating the barrel. The original production entry contains the configured_counter_count schema field. The candidate entry omits it. The eagerly mounted provider genuinely needs coordinator validation.

apps/web/src/lib/api.ts imports FacilityReadiness as a TypeScript type. The authenticated facility overview requests readiness through that typed API helper. No browser runtime consumer imports the selected validator. The contract describes facility configuration, operational services and counters; it does not parse visitor credentials or offline commands. Introducing a staff-route import would create unnecessary work. packages/contracts/src/admin.ts now marks only this side-effect-free construction as pure via a wrapped initializer. The public schema and inferred type still export normally. Consumers referencing the schema retain its original shape and validators. This concerns facility configuration readiness, distinct from the infrastructure readiness probe.

B4 changed exactly packages/contracts/src/admin.ts, this report and docs/testing/M7-evidence.md.

## Remaining graph and decision

The B3 source-map analysis remains applicable because chunk memberships match. React DOM (~54.7 KB independently gzipped), routing (~14.4 KB) and React (~3 KB) support immediate rendering and navigation. The shared entry also contains Zod (~26.9 KB), API/session code, display preferences, offline reachability, authority and reconciliation. Visitor input parsing, role/tenant enforcement, recovery credential handling and coordinator fencing must execute before their protected operations. Staff-only contract construction, coordinator management UI and optional Ask Que/push configuration present narrower opportunities. Independently compressed module sizes cannot be added as realized savings.

A separate visitor shell could avoid initializing staff session/authority machinery on anonymous entry while retaining React and the API. It requires review of cross-route session transitions, cache updates, secure deep links and cold offline staff restart. A narrower feature-local validation boundary would retain Zod, strict parsing and CSP-safe initialization while loading staff validation with the first protected workflow. Its removable share is unknown. Even removing all of the attributed Zod footprint would leave a substantial ticket gap. The current evidence establishes neither feasibility nor impossibility under the approved architecture. No measured low-risk combination covers the remaining 41–49 KB. Seek architecture review before prototyping a separate shell.
