# QueueBridge deployment readiness on RumptyCloud

**Decision requested: approve a topology for costing and staging verification only after the workspace evidence below is available.** The most direct fit is one credit-covered Linux VM running a reverse proxy and two separately supervised Node processes, plus a private managed PostgreSQL database. This is a proposed mapping. Credit eligibility, capacity, recovery and end-to-end behavior remain open. A managed static/API deployment becomes attractive if support confirms same-origin routing, response headers, streaming and a continuously running worker without an HTTP listener.

## Proposed routing and runtime configuration

Use one stable HTTPS origin. Serve apps/web/dist from the proxy. Route /api/v1/\* and /health to the Fastify upstream; route /health/ready through the approved probe policy. Match these prefixes before the SPA fallback. Serve existing JS/CSS, manifest, icons, registerSW.js, sw.js and push-handler.js with correct MIME types. Return 404 for missing assets and index.html for application navigations including /join, /ticket, /recover and protected deep links. Cache content-hashed assets long term. Revalidate HTML, registration and worker scripts so updates are discovered. Keep enough previous hashed files for open tabs. Exclude credentialed API traffic from edge caching.

Use the exact CSP, HSTS, frame, referrer, permissions and MIME policies in the repository on static responses. Preserve API headers, cookies, Origin and CSRF checks. Keep VITE_API_BASE_URL empty for same-origin API calls. Do not bake secrets into Vite output. Confirm domain-wide HTTPS suitability before enabling HSTS with includeSubDomains. ## Monitor-safe proposal requiring approval

1. Keep /health publicly reachable at the application origin for browser reconnect. Preserve its cheap DB-independent response. Keep /health/ready available to trusted monitors on a private interface/path ACL if the host supports it. Have monitors reach the existing path without a user session. Confirm behavior for GET and HEAD.
2. If private routing is unavailable, request authenticated edge-to-origin monitoring or documented probe source ranges. Reject untrusted external traffic to readiness at the proxy if feasible. Keep the origin inaccessible directly. Strip incoming forwarding headers and reconstruct them at the trusted hop. The current TRUST_PROXY flag is boolean; leave it false until the full path is constrained. Avoid a quota keyed to the shared proxy address.
3. Size the monitor allowance from actual cadence, concurrent probes, retries, rollout overlap and replica count. Each readiness request performs SELECT 1. For N replicas and M probes per replica every T seconds, baseline DB work is N × M / T queries per second before retries. Confirm reverse-proxy isolation before deciding whether very short per-instance readiness coalescing is necessary. Check maximum stale-success window against the readiness SLA.
4. Prefer an edge burst limit for anonymous liveness large enough for shared-NAT reconnects; give verified monitor traffic an independent allowance. A per-instance limit multiplies with replicas. Establish ceilings from observed legitimate bursts and platform limits. Verify external denial or 429 where intended, independent clients, healthy probe continuity and truthful readiness 503 on DB loss in staging. Avoid binding DB outages to process restart storms. Owner approves scope, source trust and numbers before any change.

## Release, recovery and approval gates

1. **Cost and platform approval.** Obtain the matrix evidence, approve region, data handling, credit envelope, DB recovery point/time objectives, backup retention and operations owner. Choose VM mapping or demonstrate equivalent managed controls. No resource creation follows from this assessment.
2. **Release approval.** Select a committed, reviewed candidate with required hosted CI. Retain commit SHA, lockfile checksum, build log and artifact digest. Use Linux-compatible Node 24 and pinned project-compatible pnpm (local evidence used 9.15.9). From repository root run pnpm install --frozen-lockfile, pnpm build and pnpm --filter @queuebridge/web bundle:check. Package web dist and runnable API/worker workspaces with production dependencies, compiled internal packages, KB assets and migration files. Prior D results remain local evidence.
3. **Database and recovery approval.** Prefer scheduled encrypted pg_dump backups to a separate credit-covered failure domain. Restore into an isolated fresh database, verify schema/history, queue sequences, hash chains, tenant access and key availability. Measure actual restore time and data loss interval. Alert on failed backups. Owner signs off before live data. [RumptyCloud restore guidance](https://docs.rumptycloud.com/databases/backups/)
4. **Staging execution approval.** After backup, run pnpm db:check, inspect identity and pending files, run pnpm db:migrate once with the release artifact, then pnpm db:check again. The migrator accepts an empty or identified consistent QueueBridge database and serializes migrations. Never seed/reset a live DB. Start API, verify readiness and schema compatibility, then start worker and switch the web release atomically.
5. **Hosted verification.** Check certificate chain and exact headers on HTML, assets, manifest, worker and API. Open a deep link in a clean profile. Verify a synthetic visitor, staff and board can sustain SSE through the edge, receive change signals promptly and pick up reconnect after disconnect. Inspect ping frames, time-to-first-event and buffering; ensure ticket tokens remain in headers. Verify polling fallback, DB notification delivery across instances if used, staff call and visual alert. Observe worker outbox lag, errors and confirmed provider receipts separately. Exercise authorized offline capture, fencing and idempotent reconciliation, saved visitor cold reopen, no landing precache on join, and a two-version worker update with an old tab open. Record evidence without sensitive payloads.
6. **Release or rollback decision.** If staging fails, hold traffic. For an application rollback retain the previous compatible web/API/worker release and static assets. Pause/drain consumers as appropriate. Preserve queued notifications and idempotency records. Check old binaries against the migrated schema before switching. An incompatible DB change requires a forward fix or separately approved recovery into a fresh DB. A restore can lose legitimate queue events and replay already-sent notifications; reconcile external receipts, fence stale coordinators and verify audit integrity before resuming service. Production deployment requires separate explicit owner approval.

Collect structured API/worker logs, request IDs, restart counts, DB pool errors, readiness transitions, worker evaluation timestamps, pending/retry outbox age and audit checkpoint freshness. Define retention and authorized readers; ensure proxy access logs exclude query strings and credentials. A live process alone cannot prove that notifications are progressing.
