# M7.3E landing specification

Anonymous visitors on narrow screens open an inline disclosure beside the brand. Tab enters the links and display settings in reading order. Escape restores focus to the trigger. Following a link closes the disclosure and uses existing route focus. Desktop and authenticated navigation keep their existing layout.

The hero pairs a concise continuity promise and facility setup action with an example visitor ticket. Product previews below show reception and facility administration using local review captures. The six-stage walkthrough follows the previews, with a framed simulation, manual controls and static reduced-motion presentation. Capability details, audience guidance, live channel availability, join instructions and role-aware setup complete the page. Saved tickets retain priority above the hero.

Use existing typography, theme surfaces, focus rings and brand accents. Keep the mobile help launcher in its dedicated safe-area space. Reserve image dimensions and load below-fold captures lazily. Review narrow and desktop renders, keyboard navigation, contrast, existing frontend regressions and bundle ceilings.

## Final acceptance verification

The complete configured Chromium and WebKit run took 11.9 minutes on disposable PostgreSQL 16. Of 394 cases, 386 passed, one failed and seven were skipped. All four WebKit smoke cases passed. The mobile Chromium smoke missed the Ask Que keyboard opening after closing display settings. Its test now waits for the dialog to unmount and focus to return before moving focus to the launcher. Five consecutive focused repetitions passed. The skips were four opt-in screenshot jobs, two desktop executions of a mobile-sheet-only check, and native Firefox print coverage.

Four separate native Firefox attempts failed before page creation. A standalone Playwright launch without QueueBridge reproduced “Could not find profile folder” and exit code 1 with revision 1572. This candidate has no native Firefox application result.

Layout.tsx now closes the disclosure on outside click and breakpoint changes. Closing on pointer-down could shift a link before activation. Shared styles restore the single mobile header row and hide Menu on desktop. Landing regressions passed at 320, 375, 390 and 430 px, including outside interaction and breakpoint transitions. Keyboard navigation, Escape, route changes, launcher clearance, dark and high contrast themes, enlarged text, reduced motion, unavailable channel responses and all six continuity stages passed their applicable checks.

The repeat phone, dark tablet and desktop screenshots matched the existing PNG files byte for byte. The three product crops also reproduced byte for byte from repository test captures. They show fictional ticket, queue and facility configuration without private customer data.

The build, formatting, lint and typecheck passed. Final gzip measurements were 137,698 bytes for entry JS, 7,290 of 7,293 for shared CSS, 25,113 for landing JS and 3,313 of 3,348 for landing CSS. Cold Chromium contexts with service workers blocked recorded the foreground JavaScript requests through network idle. Summing named files with gzip -9 gave 142,603 bytes for join, 149,506 for ticket and 141,492 for recovery. These measurements used direct sample URLs without a saved visitor credential. Each exceeds the strict visitor budget independently.

Values are gzip bytes. Exported staging SHA 565cd7e372e633451aa55bc2c363d8dff1a99cf6 with git archive, installed its frozen lockfile and ran pnpm build. Rebuilt the current working tree with pnpm build. Chromium 158.0.8127.18 opened each direct URL in a fresh anonymous context with the service worker blocked. Both builds used the same loopback origin, SPA fallback and unavailable API responses (503), without database access. After network idle, summed gzip -9 -c of every distinct requested JS file, including registerSW.js. This measures direct startup with no saved credential. It does not exercise successful API data or offline workflows. The earlier acceptance numbers differ by up to 34 bytes on the rebuilt candidate.

All routes fetch the shared entry, registration, route page, recoveryKey and tickets. Join adds format. Ticket adds format, policy and qrSvg. Staff/admin page implementations, the landing showcase and the QR encoder did not appear in the cold requests. No identical source-map source path occurred in multiple JS chunks. The entry source map includes main → App → auth and OfflineProvider, IDB, display preferences, announcement policy, PushHandoff, Ask Que help clients/store and server-facing contracts, together with React, routing and Zod. The full help panel is already lazy. The shared JS alone is 137,722 bytes. The normal bundle checker permits 197,241 and does not sum visitor route requests.

The experiment used the landing candidate source in the isolated staging copy. In its App.tsx, dynamic imports replaced eager imports for Login, Signup, AcceptInvite and DisplayBoard, with the existing Loading component as Suspense fallback. The production build succeeded. Join and ticket then fetched small shared live and useLoad chunks. Realized route savings were 1,922, 1,925 and 3,098 bytes respectively. The experiment adds four entry transitions and leaves every visitor route materially over budget. It was not retained.

The prior isolated React/router page-entry experiment measured the existing ticket page at 124,777 bytes before full credential, accessibility, registration and offline behavior. This and the current results support evaluating a ticket-first visitor entry with scoped validation and a single shared owner for session, reachability and pending operations. Its feasibility still needs a functional prototype. Deferring credential capture, validation or push listeners would risk losing a one-time handoff or a committed-turn alert. Moving staff reconciliation behind the wrong boundary could break a coordinator's cold offline restart. [Architecture experiment and parity criteria](M7.3-performance-architecture-decision.md)

The strict route gate failed before promotion. No new PWA, offline, accessibility, screenshot or complete browser regression run was performed in this phase.
