## Security and monitoring

The app uses opt-in route limits. The database regression reran authorization, tenant isolation, layered recovery throttles, join limits, invalid signatures, nonce replay, duplicate receipts and state-preservation assertions. Local tests cannot establish effective limits through a production proxy, multiple replicas or long-lived connections. An independent quota boundary assertion per public method remains incomplete as identified in A.

The confirmed exposure at application level is anonymous GET/HEAD liveness and DB-backed readiness without explicit application quotas (apps/api/src/app.ts). Readiness issues SELECT 1 per invocation. Unit coverage checks liveness and truthful readiness failure against an unreachable DB. Existing clients use /health to detect restored connectivity. Before setting a quota or private ingress policy, establish which probes are public, how client IPs are derived, which probes share addresses, how many replicas exist and how the platform handles a failed probe. A guessed per-IP limit could itself cause outages. No new exploitable authorization or integrity defect was confirmed. D made no application or ingress correction.
