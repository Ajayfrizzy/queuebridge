# M7.3 visitor performance architecture decision for review

**Status: retain the strict budget and defer production architecture approval.** Feature-local validation is the smaller intervention, but its measured opportunity falls well short of the gap. A visitor shell is the more plausible boundary. Simply putting the existing visitor pages under a smaller React root still exceeds the budget on every route, even before restoring mandatory shell behavior. Neither option currently demonstrates a safe pass.

## Baseline and isolated size experiment

On feature/m7-3-hardening at base 5d2e5ea with the accepted uncommitted B4 implementation, the shared production entry is 137,315 gzip bytes. B4 counted every startup script in fresh browser contexts, including registration. The limit is 99,999 bytes. C changed test configuration and coverage. [B4 matched measurements](M7.3-B4-schema-isolation-evidence.md)

All values are bytes. The last column compares artifacts with different functionality. It cannot be booked as a production saving.

For the experiment, copied apps/web/src into a new temporary directory, linked the installed apps/web/node_modules for resolution, and wrote all entry points and outputs there. Used Vite 6.4.5 production defaults, ES2022 and React automatic JSX. For each of four builds, index.html loaded a TSX entry importing createRoot, BrowserRouter, Routes and Route. The wildcard route rendered either an empty main element or exactly one existing visitor page (empty fragment prop for the credential routes). Ran Vite build --target es2022 separately and measured the resulting index JS with gzip -9 -c. The empty routed React root was **71,992 B**, leaving **28,007 B** for all other immediate code, including worker registration. The earlier production source-map attribution measured React DOM around 54.7 KB, router 14.4 KB, React 3.1 KB and Zod 26.9 KB independently compressed. These values cannot be summed as predicted savings. [B3 attribution and runtime measurements](M7.3-B3-implementation-evidence.md)

The probes retain transitive page imports, including current contract barrels. They omit authenticated layout, several required provider mounts, worker registration, actual fragment capture and complete accessible navigation. They were compiled, not exercised as working applications. Chunk compression and module interleaving differ from the production build. Ticket alone would need another 24,778 B removed from this stripped artifact before adding back missing behavior. The result rules out a simple entry swap as a sufficient change; it does not establish an absolute minimum.

## Dependency boundaries and tradeoffs

Today main.tsx initializes CSP-safe Zod and display preferences, then App.tsx mounts the shared router, AuthProvider, OfflineProvider, announcer, accessibility provider and Layout. Layout pulls in staff navigation and health, PushHandoff and the Ask Que launcher. Visitor routes load on demand inside that graph. TicketPage imports useOffline solely to read reachability, yet the provider module imports coordinator authority, outbox and reconciliation. Page API helper DTO imports are type-only. Runtime imports such as uuidv7 from the contracts barrel can cause unrelated schema constructors to enter the graph. The B4 experiment removed one such constructor for a **measured 102 B** shared-entry saving.

## Recommendation and owner decisions

Authorize at most a disposable **ticket-first functional prototype** of B combined with narrowly scoped A imports. Ticket has the largest deficit and exercises the most consequential credential, continuity and alert paths. Keep React 19, existing server contracts, design system, storage formats and service worker. First try the existing router. A smaller visitor routing adapter would broaden the experiment and needs explicit approval, including responsibility for browser history, fragment handling, focus and titles. Do not approve a production shell based on the stripped build numbers.

Decide whether the cost of this prototype is justified now, whether a distinct routing adapter is in scope if the first build misses, and who owns long-term parity between entries. If the functional ticket prototype still exceeds 99,999 B, stop before expanding scope. Keep performance acceptance open. A rendering framework substitution or server-rendered architecture would require its own ADR, deployment analysis and owner decision.

## Acceptance for any future implementation

1. In clean production builds, exercise cold join, direct ticket and direct recovery through meaningful interactive content and required listeners. Count registration, shared and dynamically imported startup JS. Each sum must be at most 99,999 gzip bytes. Report browser transfer bytes separately and verify the existing ceilings.
2. Verify direct entry, refresh, back/forward, join → ticket, in-memory key handoff, fresh recovery, revoked credentials, push-open references, CSRF and cross-tenant denial. Check URLs, request logs and persistent stores for secret leakage using synthetic fixtures.
3. Install and upgrade a real worker with old and new tabs open. Cold restart a previously authorized coordinator while disconnected, execute only permitted local operations, reconnect, and verify fencing, idempotency and review. Verify saved visitor ticket offline reload and offline QR. Check that unrelated installs do not fetch landing assets.
4. Verify keyboard focus and titles, large text, contrast, zoom, reduced motion, offline errors, Ask Que open/close and content gating, and committed turn alerts with visual fallback. Repeat the accepted six-cell smoke matrix and applicable full regression after implementation.
